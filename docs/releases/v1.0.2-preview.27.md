# Microsoft 365 Auth Repair v1.0.2-preview.27 — Windows security and sign-in safeguards

**Preview only — stable 1.0.1 is unchanged.**

## What's new

1. **BitLocker conversion status without elevation.** First request the read-only Win32_EncryptableVolume `ConversionStatus` property for the operating-system volume. If that property returns Unknown, attempt the previously isolated, 10-second, admin-dependent `GetConversionStatus` method as a fallback. Never infer encryption state from `ProtectionStatus=OFF`.
2. **Advanced device security** from **TPM & BitLocker → View full details → Advanced device security**. The usual Check & Diagnose and the first detail view remain read-only. Advanced is a separate dialog with explicit warnings.
3. **Admin-only BitLocker controls:** export numerical recovery password(s) to a **new local NTFS .txt** file; suspend existing OS-volume protectors until one reboot; resume protection; and start operating-system-drive decryption (which disables BitLocker and removes protectors when it completes). They require an elevated interactive administrator, explicit risk acknowledgement, an exact typed phrase and a second Yes/No confirmation. Changing settings never happens from Check & Diagnose.
4. **TPM Clear safety:** The **Open Clear TPM console** action only opens the Windows TPM Management MMC, after the same warnings and typed confirmation. The app itself never invokes `Clear-Tpm`, `Win32_Tpm.Clear`, deletes a TPM key or automatically clears anything. The operator is responsible for separate Windows confirmation and verifying recovery materials first.
5. **Recovery-password privacy:** only the OS volume and numerical (48-digit) recovery protectors are read, solely after explicit consent. Save to a newly created local NTFS .txt file, with Windows ACL restricted to the current administrator and LocalSystem. Never place passwords, protector IDs, file paths, account IDs, TPM owner secrets or command output in local Activity or a public diagnostics report. Do not export to a cloud-sync directory, network share or public folder.
6. **`.bak` cleanup after a successful update:** The verified rollback file is retained through the transactional install and the post-install GUI smoke test. Only once the new version has actually launched the main form and confirms a matching `INSTALL_OK` receipt will it remove its own `Microsoft365AuthRepair.exe.bak`. New receipts verify the exact installed/backup hashes, older Preview.26 receipts have a restrictive version check. Failed updates, version mismatch, helper-only invocations, bad hashes or denied access never delete rollback data.
7. **AADSTS70008, 700082, 700084:** Recognized as expired sign-in grants/refresh tokens. User-facing guidance prioritizes a *fresh interactive Microsoft 365 sign-in*, then checking Entra sign-in logs if it repeats. These codes alone do not call for WAM reset, TPM clear, decryption or token/cache deletion.
8. **Windows tests** cover Advanced UI wiring, argument allowlists, recovery-password shape, restricted file intent, backup cleanup decision, the existing x64/ARM64 GUI and worker tests, and SHA-256 release package checks.

## Important limitations and pilot testing

- A successful `manage-bde -off` command **starts** decryption; it does not mean decryption already finished. Follow Windows BitLocker progress before restarting or changing protectors.
- The exported .txt contains a highly sensitive recovery password. Prefer established enterprise escrow; if file export is necessary, secure it offline. Never send it through anonymous diagnostics.
- TPM Clear cannot be undone and can invalidate credentials and access to BitLocker data. An administrator must independently confirm recovery keys before using Microsoft's manual Windows TPM console.
- WMI can be unavailable due to edition, provider state or access controls. A `Not verified` result is not evidence that the disk is unencrypted, or that another encryption product is in use.
- No Microsoft 365 device sign-in is silently tested or modified by the read-only hardware probes.

## Field validation

On the affected workstation, confirm `BitLocker protection (WMI)` and `BitLocker encryption (WMI)` return independently and examine **View activity** when the card is below the fold at 200% DPI. A regular user should see Advanced tools disabled, while an elevated administrator should see the warning and both confirmation steps. Avoid executing decryption or TPM Clear during UI testing.

The reported `AADSTS70008` screenshot and Request/Correlation IDs are **not** embedded in this release or in public diagnostic schemas; only the fixed error code is recognized.
