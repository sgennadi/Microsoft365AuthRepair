# Microsoft 365 Auth Repair v1.0.1-preview.6

## What's new
1. **All users** now processes only users who already have a Windows profile on this computer. No attempt is made to repair accounts that have never signed in.
2. Existing offline profiles receive per-user Task Scheduler jobs that run under their own Windows account at their next sign-in. No password is requested.
3. These jobs use an admin-protected local worker under ProgramData, so deleting the original downloaded EXE does **not** break pending work.
4. Removed the unnecessary Preview.5 first-sign-in campaign for nonexistent profiles. Older HKLM Run registration is safely removed when an administrator next starts All users on that computer.
5. Current user retains the opt-in portable EXE cleanup after a successful repair, separate from the protected worker needed for other profiles.
6. The Update button still handles downloaded EXE replacement with verification, restart and rollback, including UAC only where required.

## Important details

- Supported scope is the list of existing, real user profiles from Windows ProfileList, including domain users whose profile directories are present. Domain accounts that never logged into this PC are out of scope.
- Task Scheduler must launch the worker in the affected person's **interactive session** (InteractiveToken / logon trigger). In Session 0 or SYSTEM the current user's WAM cannot be repaired correctly.
- The original EXE in Downloads can be removed. The protected ProgramData worker must remain until pending jobs finish or expire. The app will never delete that worker when cleaning up a portable user copy.
- If an administrator deletes the protected worker too, a local scheduled script alone is not a reliable fallback. Deploying a protected worker via GPO or Intune is a better centrally managed recovery mechanism; this is not yet automated by the application.
- The existing implementation still uses Windows PowerShell to register tasks through the Task Scheduler COM bridge and to call Add-AppxPackage. If PowerShell is blocked by policy, these steps may fail and require further native API work.
- GUI and build CI are not substitutes for actual offline user logon, UAC, AppX and multi-user field tests. Stable v1.0.0 remains unchanged.
